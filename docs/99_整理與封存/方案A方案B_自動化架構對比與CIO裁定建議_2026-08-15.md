# 方案 A／方案 B 自動化架構對比與 CIO 裁定建議

**日期：** 2026-08-15  
**適用事項：** 每日自動化清單第 1 項「是否作為每日自動化藍圖」與第 2 項「採用方案 A 或方案 B」  
**目前狀態：** 僅供裁定；沒有啟用排程、建立背景服務或執行風控計算。

## 一、先界定兩個方案真正做什麼

### 方案 A：輕量每日執行

方案 A 是在現有 CIO 直送模式上加一個固定的晚間工作入口。白天由 CIO 將新聞、截圖、群組資訊或其他原始材料放入今日工作區；晚間固定時段由 AI 載入正式文件基線，整理今日輸入，完成情報統合、引用正式風控結果、執行 Self-QA，最後封裝晚間報告與儀表板。方案 A **不應自行搜尋新聞、不應自行重算風控模型、不應把缺少的資料補猜成市場事實**。

方案 A 的核心是把「現有人工輸入＋AI 晚間統合」固定化，而不是建立完整的市場資料管線。風控仍由正式風控官流程產出；戰情室只引用正式風控結果。

### 方案 B：分離式自動化

方案 B 把可程式化、可重複驗證的工作從語意分析中分離出來，例如收盤資料取得、交易日判定、MA21／MA81 計算、資料完整性檢查、固定格式輸出與執行紀錄。AI 只在需要語意判斷、事件統合、深度研究或晚間敘事封裝時介入。

方案 B **不是授權程式自行創造或修改風控模型**。程式只能依正式風控規格書與風控官執行介面執行；若正式規格變更，必須先完成上位文件修訂、版本紀錄與 CIO 核准，再同步更新程式。

## 二、整體比較

| 比較面向 | 方案 A：輕量每日執行 | 方案 B：分離式自動化 |
|---|---|---|
| 建置速度 | 快，可在現有流程上加固定入口 | 慢，需要資料管線、程式、測試、監控與持續運行環境 |
| 現行模式相容性 | 高，直接延伸 CIO 直送模式 | 中，需要重新定義程式與 AI 的邊界 |
| 每日操作依賴 | 高度依賴 CIO 白天提供資料 | 對固定資料工作依賴較低，但語意情報仍依賴 CIO 或明確授權來源 |
| 資料處理可重現性 | 中低，同一批輸入可能因模型與上下文而有差異 | 高，計算、驗證、時間與格式可固定化 |
| 風控計算可靠性 | 只有在引用正式風控結果時才可靠；不可由晚間統合自行重算 | 若資料源、公式、交易日與測試正確，計算可重複；但程式錯誤會造成系統性錯誤 |
| 模型處理量與延遲 | 每晚需要較完整的 AI 處理 | 固定計算交給程式，AI 只處理必要語意工作，資源與延遲較可控 |
| 故障影響範圍 | 單一晚間任務失敗可能同時影響統合、Self-QA、儀表板與歸檔 | 可將資料、風控、分析、封裝、歸檔分段重試，故障較容易隔離 |
| 維護難度 | 低至中，主要維護提示、輸入規則與歸檔流程 | 高，需要 API、資料格式、程式版本、監控、重試、權限與部署管理 |
| 審計追溯 | 依賴工作區、輸出與交接紀錄是否完整 | 可保存原始資料、計算中間值、版本、時間戳與執行 log，追溯性較強 |
| 治理變更敏感度 | 低，主要是執行既有流程 | 高，任何規格、欄位或計算邏輯變更都可能影響程式與正式文件 |
| 適合階段 | 立即試運行、低風險驗證 | 長期正式化、規模化與可重複執行 |

## 三、方案 A 的具體優缺點與風險

| 類別 | 優點 | 缺點／風險 | 必要控制 |
|---|---|---|---|
| 流程 | 與現行 CIO 直送模式一致，無需立即改造角色鏈 | 白天沒有輸入時，晚間流程可能只得到「無新增資料」；不能自行補齊情報 | 將「無今日輸入」設為正常可交付狀態，不得自動補造新聞 |
| 建置 | 不需先建立持續運行的資料服務，較容易試行與停用 | 容易把多個工作塞進單一晚間任務，失敗時不易定位 | 將基線載入、風控引用檢查、統合、Self-QA、封裝、歸檔分成可辨識步驟 |
| 風控 | 可以嚴格遵守「戰情室只引用風控官正式結果」 | 若執行者誤把 MA21／MA81 重新計算，會違反唯一 SSOT 原則 | 明確禁止方案 A 自行重算；只讀取風控官正式輸出與時間戳 |
| 資料品質 | CIO 可先過濾來源，減少無關訊息 | 輸入品質與完整性受 CIO 提供方式影響；可能遺漏來源、時間或原始連結 | 今日工作區採固定收件格式，至少保留原始內容、來源、時間與待查事項 |
| 重跑 | 操作簡單，人工可以重新要求執行 | 重跑可能重複產生報告、重複歸檔或覆蓋前次結果 | 每次執行使用日期＋批次 ID；禁止無標記覆蓋既有輸出 |
| 治理 | 不必立即把草案升格為正式作業文件 | 若直接設成每日固定排程，可能被誤解為 CIO 已核准整份治理藍圖 | 先標示「試運行／未啟用正式自動化」，保留 CIO 核准與停止條件 |
| 維護 | 維護面較少，容易暫停或調整 | 依賴單次提示與上下文，長期可能出現輸出漂移 | 固定基線清單、版本標記、Self-QA 與輸出模板；不靠模型記憶補規則 |

### 方案 A 的主要風險排序

方案 A 最大的風險不是程式錯誤，而是**輸入缺口被誤認為市場沒有事件、或 AI 在晚間統合時自行補齊缺失資料**。第二個風險是**把晚間統合誤當成風控執行**，導致分析閘門重算正式水位。第三個風險是**單一任務過度集中**，使報告、Self-QA、儀表板與歸檔同時受到一次失敗影響。

## 四、方案 B 的具體優缺點與風險

| 類別 | 優點 | 缺點／風險 | 必要控制 |
|---|---|---|---|
| 計算 | 收盤價、MA21／MA81、交易日與資料完整性可重複執行 | 公式、時區、交易日、缺值或公司行動處理錯誤會產生系統性錯誤 | 以正式規格書為 SSOT；建立固定測試案例、邊界測試與人工抽查 |
| 資料源 | 可保留原始資料、抓取時間、版本與計算中間值 | API 中斷、資料延遲、欄位改名、來源修正或授權失效都會影響結果 | 多層資料驗證、來源狀態標記、失敗告警；資料不足時停止判定 |
| 重現性 | 相同輸入與版本通常能得到相同結果，適合稽核 | 程式若未鎖定版本或未保存輸入，事後仍可能無法重現 | 保存程式版本、規格版本、資料快照、執行時間與結果雜湊 |
| 故障隔離 | 可將收盤資料、風控、分析、封裝、歸檔分開，逐段重試 | 分散式流程增加狀態同步、重試與重複執行的複雜度 | 每個步驟建立明確輸入／輸出契約與冪等鍵，不得重複產出正式結果 |
| 安全 | 可限制 AI 只接收已驗證資料與必要欄位 | 需要管理 API 金鑰、資料權限、持續服務與執行環境 | 秘密管理、最小權限、操作 log、輪替機制與異常停機流程 |
| 治理 | 程式與正式規格分離後，規則本體較容易被固定與審計 | 程式可能逐漸累積未經核准的「方便性規則」，形成影子模型 | 任何規則改動先改上位正式文件，再更新程式；由 CIO 核准生效 |
| 維護 | 長期可擴充，適合增加資料驗證與固定輸出 | 需要持續維護依賴套件、資料源、部署、監控與回溯工具 | 建立維運責任、版本退回、健康檢查、失敗通知與定期演練 |

### 方案 B 的主要風險排序

方案 B 最大的風險是**自動化程式看似客觀，實際上把未經核准的假設固化成計算規則**。其次是**資料源或交易日判定錯誤造成整批結果錯誤**，再其次是**程式正常回傳但資料已過時或不完整，形成靜默失敗**。因此方案 B 的核心控制不是「讓程式自己決策」，而是讓程式只做可驗證的資料與計算工作，遇到不確定性就停止並通知。

## 五、治理符合性比較

| 治理要求 | 方案 A | 方案 B |
|---|---|---|
| CIO 是最終裁定者 | 可符合；晚間 AI 不得自動完成治理裁定 | 可符合；程式不得自行改變正式水位或投資決策 |
| 風控規格書是唯一風控 SSOT | 可符合，但必須禁止晚間流程重算 | 可符合，但程式必須明確版本化並只實作已核准規格 |
| CIO 直送模式 | 高度符合 | 固定資料工作可自動化，但每日語意情報仍須遵守 CIO 直送邊界 |
| 上位文件先修訂、下位文件後引用 | 較容易維持 | 需要把程式、模板、SOP、INDEX 一併納入同步檢查 |
| 可追溯與可回退 | 中等，依輸入與輸出歸檔紀律 | 較強，但前提是保存資料、程式與規格版本 |
| 目前是否可以直接啟用 | 不可，仍需第 1、2、6 項裁定 | 不可，還需建置規格、測試與正式治理核准 |

## 六、CIO 的裁定方式

### 第 1 項：是否可把清單作為每日自動化藍圖

不建議直接批准為「正式自動化藍圖」。較精確的裁定文字應為：

> **可作為非正式試運行設計草案，不代表已核准啟用、不得建立正式排程、不得取代現行風控官流程；待三層閘門角色邊界、版本 Diff、Drive 輸出位置與停止條件補齊後，再提出正式升格。**

這樣可以保留清單的工作價值，又不會把目前尚未完成核准的治理架構一併視為已生效。

### 第 2 項：若目前必須在 A 與 B 之間選擇

若目標是**先驗證每日流程是否穩定**，建議選擇 **方案 A 作為受限試運行**，但只自動化基線載入、情報統合、正式風控結果引用檢查、Self-QA 與輸出封裝；不能自行新聞蒐集、不能自行計算風控水位、不能自動產生治理裁定。

若目標是**長期降低人工重複工作、建立可稽核的正式資料管線**，方案 B 才是較適合的目標架構；但 B 不應直接上線，應先完成一個不產生正式持股決策的影子驗證階段，與正式風控官結果逐日比對，經 CIO 核准後才可考慮正式接管固定計算工作。

因此最穩妥的治理路徑不是把 A、B 當成互斥終局，而是：

**A 受限試運行 → 驗證輸出與歸檔 → B 影子計算 → CIO 核准後分離式正式化。**

這條路徑仍保留 CIO 最終裁定權，也避免在尚未補齊版本與資料治理前，直接建立不可見的影子風控模型。
