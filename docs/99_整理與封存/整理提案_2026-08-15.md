# AI 投資總部整理提案

**提案日期：** 2026-08-15  
**整理基線：** Google Drive `AI投資總部憲章_v1.8.0.md`、`AI投資總部知識索引_v1.3.md`、`每日戰情室作業規範_v2.3.md`；GitHub `main` 分支現況  
**提案性質：** 非破壞性整理方案，正式文件的移動、改名、內容同步與封存須經 CIO 確認後分批執行

## 一、整理目標

本次整理的目標不是重寫投資規則，而是讓 Google Drive、GitHub Repository 與每日執行流程具有同一套可追溯的文件定位。整理後，任何人或 AI Agent 應能在幾分鐘內回答四個問題：哪一份文件是現行權威、這份文件負責什麼、它引用哪些上游資料、日常工作應從哪裡開始。

整理遵循 AI 投資總部憲章所定義的六類文件分類、上位文件先修訂原則、Single Source of Truth、保留歷史內容與不得以聊天紀錄取代正式文件等要求。本提案不自行改寫風控模型、分析框架或家庭投資中心資料。

## 二、建議的 Repository 目錄

README 已宣告下列五個正式文件目錄，建議將此宣告落實為實際結構；`portfolio/`、`templates/` 與市場資料則維持為執行支援區，不混入正式治理文件。

```text
AI_Investment_HQ/
├── docs/
│   ├── 00_治理文件/
│   ├── 01_分析框架/
│   ├── 02_作業流程/
│   ├── 03_市場研究/
│   ├── 90_版本紀錄/
│   └── 99_整理與封存/
├── portfolio/
├── templates/
├── data/
├── scripts/
└── README.md
```

`99_整理與封存/` 只存放歷史版本、草稿、已撤回提案與整理紀錄；不得將封存內容當作現行正式依據。市場 CSV 與更新腳本建議由目前深層的 `docs/00_…/data`、`docs/00_…/scripts` 移至根目錄 `data/`、`scripts/`，但這一項需先確認是否有外部腳本或連接器依賴既有路徑。

## 四、現行版與歷史版規則

現行正式文件採用不帶版本號的穩定檔名，版本號只放在文件標頭與版本紀錄。索引同樣引用穩定檔名，不鎖定某一版號；文件本身的版本紀錄才是現行有效版本的判定依據。帶有 `_v1.1`、`草案`、`Draft`、`Proposal`、`Session` 或已撤回模型名稱的文件，若仍有保存價值，應移入 `99_整理與封存/`，並在檔名前保留日期或原始版本以維持可追溯性。

不得以刪除方式清理重複文件。對於兩份內容相近的文件，應先建立「保留哪一份為現行版、另一份為歷史版」的對照紀錄，再執行移動或改名。

## 五、Drive 與 GitHub 的同步原則

目前 Drive 是較新的治理基線：憲章為 v1.8.0、知識索引為 v1.3、每日戰情室作業規範為 v2.3。GitHub 對應文件仍有 v1.7.0、v1.1 與 v2.0 等較早內容，且部分文件仍使用 GPT／Claude 舊角色描述。因此，第一輪同步應採「Drive 現行版覆蓋 GitHub 對應正式文件」的候選方案，但不應在未確認檔案對應與外部依賴前直接覆蓋。

| 同步批次 | 內容 | 原因 |
|---|---|---|
| 第一批 | 憲章、知識索引、協作治理架構、每日戰情室作業規範 | 直接決定角色、文件優先順序、每日流程與引用路徑 |
| 第二批 | 正式輸出格式、AI 基本面框架、儀表板格式規格 | 決定正式輸出品質與決策層輸入 |
| 第三批 | 風控正式規格書、風控官正式指令工作及相關治理紀錄 | 建立風控平行流程與唯一模型來源 |
| 第四批 | 研究文件、家庭投資中心與模板 | 補齊研究內容與執行支援，需逐檔確認是否有新版本 |

## 六、已發現且需在同步時處理的衝突

| 衝突 | 判定 | 建議 |
|---|---|---|
| GitHub 憲章 v1.7.0 vs Drive 憲章 v1.8.0 | Drive 較新 | 以 Drive v1.8.0 作同步候選基線 |
| GitHub 索引 v1.1 vs Drive 索引 v1.3 | Drive 新增風控導覽與版號標示規則 | 先同步索引，再同步被索引文件 |
| GitHub 協作文件仍以 GPT／Claude 為主要角色 | 與 Drive 三層閘門公告不完全一致 | 同步時保留歷史脈絡，但清除現行流程中的舊角色殘留 |
| Drive 最新協作文件仍有「提供予 GPT」等殘留句 | 同一文件內部存在角色名稱漂移 | 列為內容校準項，不在單純搬檔時自行改寫 |
| GitHub SOP v2.0 vs Drive SOP v2.3 | Drive 新增正式風控結果引用、歸檔與規則異動通知 | 以 Drive v2.3 作候選基線 |
| Drive 文件地圖列出風控文件，但目標投資總部資料夾未直接列出 | 風控正式文件位於 Drive `10_風控官` 子資料夾 | 在 Index 與 README 中建立明確跨資料夾連結 |
| 根目錄與 `docs/` 各有 CHANGELOG | 版本紀錄可能分叉 | 先建立唯一權威候選，再將另一份保留為歷史或合併後封存 |
| `templates/Daily_War_Room_Template.md` 為空 | 正式模板缺口 | 從 SOP 與輸出規範生成候選模板，另行送 CIO 確認 |

## 七、執行順序

第一階段只建立目錄說明、文件映射與同步清單，不移動、不刪除、不覆蓋正式文件。第二階段在 CIO 確認同步基線後，逐批把 Drive 現行文件匯入 GitHub，使用 Conventional Commit 並附上每一檔的來源 ID、來源修改時間與同步理由。第三階段才處理路徑移動、歷史封存、模板補齊與資料腳本路徑調整。每一批變更完成後，均須執行全文引用檢查與版本紀錄更新。
