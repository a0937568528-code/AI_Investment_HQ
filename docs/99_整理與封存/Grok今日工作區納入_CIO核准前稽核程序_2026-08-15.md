# Grok 郵件納入今日工作區｜CIO 核准前稽核程序

> **目前實作邊界：** Apps Script 已完成 Gmail→Drive `00_Grok` 原始保存、去重、處理標籤與早晚觸發；今日工作區的狀態集合、`source_channel`、`verification_agent` 與 `review_status` 尚待補實作與測試證據。

**文件日期：** 2026-08-15
**適用對象：** Grok→Gmail→Apps Script→Drive→今日工作區正式資訊來源與 Manus 驗證介面
**稽核目的：** 在 CIO 決定是否正式納入前，逐項確認來源地位、資料完整性、下游隔離、運維可控性及版本治理證據。
**目前狀態：** 稽核程序草案；不代表任何一項已通過，也不直接修改 SOP v2.3、INDEX v1.3 或每日自動化工作清單。

> **稽核總原則：** 「正式登錄來源」不等於「已驗證內容」；「能匯入」不等於「Manus 已完成核查」；「進入今日工作區」不等於「可進入正式分析」；「CIO 核准介面」不等於「授權自動決策」。

## 一、稽核結果的四種狀態

每一項只能使用下列四種狀態，不使用「大致通過」「應該沒問題」等模糊字眼。

| 狀態 | 意義 | 可否進入下一步 |
|---|---|---|
| 通過 | 證據完整，符合通過門檻，沒有未解決的阻斷缺口 | 可以 |
| 有條件通過 | 核心風險已被限制，但仍有明確待補事項；必須由 CIO 接受條件 | 只能進入受限試運行，不得升格正式規則 |
| 不通過 | 存在來源、資料、權限、下游隔離或版本治理阻斷問題 | 不可以；先停用或維持原始保存 |
| 待 CIO 裁定 | 技術證據足夠，但涉及治理效力、採信程度或正式版本升級 | 停在裁定點，不得自行推進 |

## 二、開始稽核前的固定準備

稽核人員先建立一份稽核批次紀錄，欄位至少包含稽核日期、資料截止時間、Apps Script 專案名稱、專案時區、Drive 根資料夾、Gmail 查詢條件、目前 SOP／INDEX／憲章／風控文件名稱與版本、目前觸發器時間，以及此次稽核使用的測試郵件數量。

接著固定保存四組證據：第一組是 Drive `00_Grok` 的原文檔案與日期資料夾；第二組是 Apps Script 的設定、執行紀錄與觸發器清單；第三組是 Gmail 測試郵件的寄件者、主旨、收到時間與 thread／message ID；第四組是現行 SOP、INDEX、憲章、風控規格與每日自動化清單的版本快照。

若任何一組證據無法取得，稽核不得直接判定通過，應標記「待確認」並停止進入正式納入裁定。

## 三、六項核准前檢查的逐項稽核程序

### 檢查 1：確認 Grok 是正式資訊來源之一，且內容必須經 Manus 驗證

**稽核問題：** CIO 是否同意正式登錄 Grok 為資訊來源之一，並要求所有數據、新聞、來源、時間、證據與推論先經 Manus 驗證，才取得正式分析支持性效力？

**具體步驟：**

1. 從一封已匯入郵件保存寄件者、主旨、收到時間、正文、原始連結、Gmail message／thread ID 與 Drive 檔案位置。
2. 將郵件內容拆成三類：Grok 自身摘要或推論、Grok 引用的原始事實、仍需核對的主張。
3. 確認每個項目都有初始狀態 `已匯入`、`未驗證`、`待 Manus 驗證`、`Manus 已完成核驗` 或 `可作正式分析支持性輸入`，而不是 `已確認`、`正式結論` 或同等字樣。
4. 檢查今日工作區的輸入標記是否能顯示 `source_channel=Grok`、`verification_agent=Manus`、`third_party_ai_summary=true` 與 `review_status=未驗證／待 Manus 驗證`。
5. 將「待狀態索引完成後自動納入今日工作區」與「正式分析支持性輸入」分成兩個獨立欄位，不能用單一 `processed=true` 同時代表兩者。

**必要證據：** 一封原始 Grok 郵件、對應 Drive 檔案、今日工作區輸入標記範例、來源／審核狀態欄位截圖或文字紀錄。

**通過門檻：** 每個自動匯入項目都能追溯到原始郵件；預設是未驗證／待 Manus 驗證的正式資訊來源內容；沒有任何自動匯入標記會暗示 Manus 已完成核驗、CIO 已採信或正式分析已完成。

**失敗處置：** 若自動匯入直接標示為已確認、正式結論或投資建議，立即停止今日工作區的自動納入，只保留 `00_Grok` 原始檔案，並修正狀態欄位後重新測試。

**CIO 裁定輸出：** `核准／有條件核准／不核准`；若核准，裁定文字應為「核准 Grok 正式資訊來源與 Manus 驗證介面」，不能寫成「核准 Grok 結論」或「核准未驗證內容」。

### 檢查 2：確認自動匯入進入今日工作區資訊來源集合的方式與邊界

**稽核問題：** 是否允許符合條件的 Grok 正式資訊來源內容待狀態索引完成後加入今日工作區的「未驗證／待 Manus 驗證集合」，但不繞過既有資料治理要求？

**具體步驟：**

1. 用一封有效 Grok 郵件與一封不應納入的郵件各做一次測試。
2. 確認有效郵件進入指定日期的資訊來源位置，並保留來源、匯入時間與 Manus 驗證狀態。
3. 確認不符合寄件者、主旨、Gmail 標籤或時間條件的郵件不會進入資訊來源集合。
4. 確認自動匯入只建立「未驗證／待 Manus 驗證／待分級」資料，不自動啟動九欄、風控、儀表板、深度研究或結案摘要。
5. 檢查當日沒有 CIO 其他輸入時，系統是否能明確標示「本日資料包含 Grok 正式資訊來源，尚待 Manus 驗證」，而不是假設今日已有完整且已核驗的情報。
6. 以一封無原始連結或內容不完整的 Grok 郵件測試，確認它可以被保存但會停在待驗證，不會被當成正式框架級情報。

**必要證據：** 有效／無效測試各一筆、今日工作區未驗證／待 Manus 驗證資訊來源集合紀錄、未觸發下游流程的執行紀錄、資料不足或待驗證標記。

**通過門檻：** 自動匯入只完成輸入與保存；下游正式分析需另有明確的分級與引用步驟；無效來源不會靜默進入工作區。

**失敗處置：** 若自動匯入能直接產出正式分析或無效郵件也被納入，停止觸發器，保留原文於 `00_Grok`，將介面狀態降回「只保留原始保存」並重新修正篩選與狀態機。

**CIO 裁定輸出：** 明確選擇「正式資訊來源自動納入並由 Manus 驗證」或「只保存、仍由 CIO 手動提升至今日工作區」。兩者不可同時以含糊方式存在。

### 檢查 3：確認目前實作設定、資料契約與資料血緣

**稽核問題：** 目前 `noreply@x.ai`、`New login` 排除條件、`00_Grok`、07:00／20:00 觸發器與去重機制，是否足以重現這條資料流？

**具體步驟：**

1. 保存 Apps Script 的 `GMAIL_QUERY`、Drive 根資料夾 ID、專案時區、早晚觸發器時間、處理標籤與錯誤標籤。
2. 在 Gmail 以實際查詢條件執行只讀測試，確認只抓到 Grok 報告，不抓到 SpaceXAI `New login` 通知或其他 `noreply@x.ai` 郵件。
3. 確認每封匯入檔案包含來源、原始主旨、收到時間、匯入時間、thread／message ID、Drive 位置與原文。
4. 以同一封郵件重跑一次，確認 `AIHQ/Processed` 標籤與檔名去重會略過，不產生第二個正文檔。
5. 以內容不同但主旨相同的測試郵件確認系統不會只按主旨誤判為重複；必要時以 message ID 或內容雜湊區分。
6. 確認錯誤時會加上 `AIHQ/Error`、保存錯誤紀錄並通知，而不是把失敗當成成功。
7. 以 Apps Script 的時區設定核對 07:00／20:00 的實際解讀，避免 Grok 與匯入時間跨日造成日期資料夾錯置。

**必要證據：** Apps Script 設定快照、成功與重跑執行紀錄、Gmail 查詢結果、Drive 檔案內容、處理／錯誤標籤與觸發器清單。

**通過門檻：** 任何稽核人員都能依紀錄重建「哪封郵件、何時收到、何時匯入、保存在哪裡、是否已處理、後續是否進入分析」。

**失敗處置：** 若資料血緣缺欄、查詢條件過寬、去重不可靠或時區錯置，維持原始保存但暫停今日工作區納入；不可直接以人工猜測補上血緣欄位。

**CIO 裁定輸出：** 核准目前介面設定、要求補強資料契約，或要求改用新的來源／資料夾／時間規則。

### 檢查 4：確認來源核對、證據拆分與資訊分級閘門

**稽核問題：** Grok 正式資訊來源中的數據、新聞與推論，在進入正式分析前是否已由 Manus 完成來源、數據、時間、證據與資訊分級驗證？

**具體步驟：**

1. 選取至少三種測試內容：一封含官方事實與 Grok 解讀的混合郵件、一封只有市場評論的郵件、一封含家庭投資中心持股影響的郵件。
2. 由 Manus 先執行 Temporal QA，核對日期、現任主體、財報期別與新聞／數據時間。
3. 將每封郵件拆成獨立證據單位，分別標示事實／推論／待驗證。
4. 對官方公告、財報或法說內容，保存或取得一手來源後再判定證據等級；Grok 自身敘述不能替代一手來源。
5. 依 SOP 分為框架級情報、背景事件或短線操作情報；不允許因 Grok 標題聳動就自動升級為框架級情報。
6. 確認只有框架級情報與需正式判定的背景事件才進九欄；短線操作情報不得自動觸發 Framework Update。
7. 對同一郵件內證據等級不同的子項分開建立記錄，不使用整封郵件的單一總評。

**必要證據：** 三種測試郵件、來源核對紀錄、證據拆分表、資訊分級結果、待驗證清單與九欄進入紀錄。

**通過門檻：** Manus 的驗證與分級結果可由引用的證據與規則重現；沒有任何項目只因 Grok 摘要而被標示為已獲確認；缺少一手來源或數據無法重現時明確維持待驗證。

**失敗處置：** 若未經核對即進九欄或被標示已確認，撤回該筆正式分析引用，保留原始文件與錯誤紀錄，重跑來源核對與分級；必要時暫停整批自動納入。

**CIO 裁定輸出：** 是否接受「未核對項目可先以待驗證支持性輸入保存」，以及哪些來源類型必須先完成一手來源核對才能進九欄。

### 檢查 5：確認下游正式流程與風控完全隔離

**稽核問題：** Grok→Drive 是否不會自動啟動或改寫正式分析、風控、儀表板、深度研究及治理流程？

**具體步驟：**

1. 使用含 MA21／MA81、持股水位或極端波動文字的測試郵件，觀察是否會觸發風控計算或產生持股水位。
2. 使用含「框架更新」「建議減碼」或「啟動深度研究」文字的測試郵件，確認不會直接生成正式判定或執行研究。
3. 確認風控官仍只讀取正式收盤資料與正式風控規格，戰情室只引用風控官正式結果。
4. 確認儀表板只能讀取已完成 Self-QA 的正式文字、風控官結果與 Portfolio 影響，不會讀取 `00_Grok` 原文直接產生結論。
5. 確認沒有任何 Apps Script 函式、Gmail 標籤或 Drive 觸發流程會修改憲章、SOP、INDEX、風控規格或 Portfolio。
6. 確認未經 CIO 核准的 Grok 輸入不會啟動深度研究或結案摘要。

**必要證據：** 下游觸發測試紀錄、風控官執行紀錄、儀表板輸入紀錄、Apps Script 函式清單與 Drive 寫入權限範圍。

**通過門檻：** Grok 管線只新增正式資訊來源原文與未驗證／待 Manus 驗證資料；任何正式分析、風控、儀表板、研究、結案與治理修訂都需要 Manus 驗證、既有流程與明確條件。

**失敗處置：** 立即停用 `processGrokEmails` 的工作區納入功能，但可保留原始郵件保存；撤回任何由 Grok 直接觸發的正式輸出，並建立治理異常紀錄。

**CIO 裁定輸出：** 明確核准的下游邊界，以及禁止自動觸發的功能清單。

### 檢查 6：確認版本治理、Diff、運維與回退能力

**稽核問題：** 若正式納入，是否能在未來規則變更、來源改變或錯誤發生時停止、回退與追溯？

**具體步驟：**

1. 建立 SOP v2.3→v2.4 的 Diff Summary 草案，列出新增章節、修改章節、不變章節、受影響輸出與不受影響的風控規格。
2. 建立 INDEX v1.3→v1.4 的 Diff Summary 草案，確認只新增輸入介面導航，不改變正式文件讀取順序與 Single Source of Truth。
3. 將 Grok→Drive 的查詢條件、時區、觸發器、資料夾、標籤、去重規則與停止方式保存為介面設定紀錄；不要把個人密碼或 OAuth token 寫入文件。
4. 測試 `stopTimeTrigger`，確認能停止自動匯入而不刪除 Gmail 或 Drive 原始資料。
5. 測試來源變更情境：寄件者變更、主旨變更、郵件延遲、Drive 寫入失敗、連續兩次無信件，確認系統會標記錯誤或通知而不靜默放寬條件。
6. 確認回退後，現行 CIO 直送模式仍可獨立運作，不依賴 Grok→Drive 才能完成每日戰情室。
7. 將 CIO 核准範圍、核准日期、生效日、停止條件、受影響文件與手動同步對象寫入治理決策紀錄。

**必要證據：** 兩份 Diff Summary、介面設定紀錄、停止／回退測試紀錄、錯誤處理測試、版本與核准紀錄草案。

**通過門檻：** 可以安全停止與回退；任何新規則都有版本與 Diff；原有 CIO 直送模式不被破壞；未經 CIO 核准的內容不會被標示為生效。

**失敗處置：** 不得升版、不修改正式 SOP／INDEX、不啟用正式納入；保持目前「原始保存」模式，直到 Diff、回退與核准紀錄補齊。

**CIO 裁定輸出：** 核准範圍、生效日、受影響文件、停止條件、是否要求寫入治理決策紀錄，以及是否允許由草案升格為 SOP v2.4／INDEX v1.4。

## 四、稽核執行順序與停損門

六項檢查不得任意跳過。建議順序是：先做來源地位與輸入邊界，再做資料契約與血緣，接著做來源核對與資訊分級，最後才做下游隔離、版本治理與回退測試。

以下任一情況出現，應立即停止，不進入下一項：自動輸入被標示為已驗證或正式結論；來源與 Gmail 查詢條件無法重現；無法取得原始郵件或 Drive 位置；未經核對直接進入九欄；Grok 輸入觸發風控或持股水位；沒有可用的停止／回退方法；或 SOP／INDEX 升版沒有獨立 Diff Summary。

## 六、正式核准的最低條件

只有在以下條件全部成立，才可以進入「是否升版並正式寫入 SOP／INDEX」的裁定：六項檢查沒有「不通過」；第 1、2 項的治理效力由 CIO 明確裁定；第 3 項的資料血緣可重現；第 4 項的待驗證與來源分級邏輯通過測試；第 5 項確認不會觸發風控或正式下游結論；第 6 項完成 Diff、停止、回退與人工同步紀錄。

即使六項全部通過，也只能表示「具備正式資訊來源驗證與升版的條件」，不代表系統自行取得核准。最後仍須由 CIO 明確指定是否核准 Grok 資訊來源介面、是否升版 SOP／INDEX、何日生效，以及哪些下游功能保持禁止自動觸發。
