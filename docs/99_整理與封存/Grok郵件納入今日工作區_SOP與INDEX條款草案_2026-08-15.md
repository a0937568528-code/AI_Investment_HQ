# Grok 郵件正式納入今日工作區｜SOP 與 INDEX 條款草案

**草案日期：** 2026-08-15  
**草案狀態：** 待 CIO 核准；尚未生效，不得直接覆蓋現行 SOP v2.3 或 INDEX v1.3。  
**提案版本：** CIO 核准後，SOP 預計升為 v2.4；INDEX 預計升為 v1.4。實際版號、生效日與變更範圍由 CIO 裁定。  
**提案目的：** 將目前已運作的 Grok→Gmail→Apps Script→Drive 資料流，正式定義為 AI Investment HQ 的**正式資訊來源與驗證介面**；Grok 可提供新聞、數據、事件線索與第三方 AI 摘要，但所有內容必須先經 Manus 完成來源核對、數據驗證、時間／期間核對、證據拆分與 Self-QA，才可進入正式分析或下游輸出。

> **核心原則：** 正式登錄來源不等於已驗證內容；自動進入今日工作區不等於 Manus 已完成核查；只有通過 Manus 的數據、新聞、時間、證據與 Self-QA 驗證，才可進入正式分析。

## 一、先定義本次提案的正式範圍

本提案只處理**輸入介面**：Grok 郵件如何保存、如何進入今日工作區、如何標記來源、如何去重、如何等待資訊分級與後續分析。它不新增 AI 基本面指標，不修改 MA21／MA81 與 100／80／80／0 風控模型，不修改九欄固定值，不修改家庭投資中心內容，也不授予任何 AI 自行更新正式文件或作出最終裁定的權限。

Grok 郵件在本提案中的來源身分是「正式登錄的第三方 AI 資訊來源」，可提供研究摘要、新聞與數據線索；其內容在 Manus 完成核驗前，仍維持未驗證狀態。Grok 所引用的原始連結、官方公告、財報或法說內容，必須與 Grok 的解讀分開保存與分級；若原始來源未被獨立核對，Grok 的敘述預設只能標示為**待驗證**，不得直接標示為已獲確認。

## 二、SOP v2.4 條款草案

以下條文建議插入現行 SOP v2.3 的「每日情報統合流程（Daily Intelligence Integration）｜CIO 直送模式」之後，作為新的輸入介面節；不建議重寫現行 CIO 直送模式，也不建議把 Grok 輸入寫成新的治理角色或新的決策閘門。

### 建議新增節：外部原始情報輸入介面（Grok→Drive→今日工作區）

**（草案條文 1｜定位與效力）**

Grok→Drive 資料流是 AI Investment HQ 的正式資訊來源與驗證介面。其功能是將符合條件的 Grok 郵件保存至指定 Drive 原始情報資料夾，並以「未驗證／待分級／待 Manus 驗證」狀態提供給今日工作區；經 Manus 完成核驗後，才可成為正式分析的支持性輸入。該資料流不改變 Constitution、Daily War Room SOP、AI 基本面追蹤框架、Risk Control 或 Portfolio 的優先順序。

**（草案條文 2｜來源身分）**

Grok 郵件的來源標記必須至少包含：`source_channel=Grok`、`verification_agent=Manus`、實際寄件者、Grok 任務或主旨、郵件收到時間、匯入 Drive 時間、原始郵件識別碼、Drive 原始檔案位置及可取得的原始連結。Grok 的文字、推論、摘要與市場解讀，均不得在未經 Manus 完成數據、新聞來源、時間／期間、證據與 Self-QA 核對前被視為已確認事實。

**（草案條文 3｜輸入範圍）**

只有符合 CIO 登錄的寄件者、主旨或 Gmail 標籤條件之郵件，才可由自動流程匯入 `00_Grok` 原始情報資料夾。未符合條件的郵件不得因同一寄件者網域或相似文字而自動納入。若寄件者、主旨格式、郵件結構或匯入資料夾改變，系統應暫停該批自動納入並通知 CIO，不得靜默放寬篩選條件。

**（草案條文 4｜原文保存與不可覆蓋）**

自動匯入應保留郵件正文、原始主旨、寄件者、收件者、收到時間、郵件 thread／message 識別碼、附件及原始來源連結。匯入程序不得刪除 Gmail 郵件、不得預設標記已讀、不得預設封存。相同 thread 或相同 message 已成功匯入者，不得再次建立未標記的新副本；若內容重新寄送或內容雜湊不同，應建立新版本並保留兩者的關聯。

**（草案條文 5｜今日工作區接收狀態）**

經自動匯入的 Grok 正式資訊來源內容，進入今日工作區時必須帶有 `未驗證`、`待分級`、`待 Manus 驗證` 或同等狀態標記。今日工作區接收只表示資料已進入當日資訊來源集合，不表示 Manus 已完成核查，也不表示資料已取得正式分析或 CIO 決策效力。

若當日沒有 CIO 直接提供的其他資料，Grok 郵件仍可作為正式登錄資訊來源輸入；但正式分析必須明確揭露資料來源與 Manus 驗證狀態，並依證據規則區分原始事實、Grok 解讀、Manus 已核驗內容與尚待驗證事項。

**（草案條文 6｜資料契約）**

每筆進入今日工作區的 Grok 輸入，至少應能取得下列欄位：

| 欄位 | 必要性 | 用途 |
|---|---|---|
| 來源通道 | 必要 | 固定為 Grok；已列入正式資訊來源清冊 |
| 實際寄件者 | 必要 | 驗證是否符合來源白名單 |
| 任務／主旨 | 必要 | 區分早報、晚報、AI 市場報告及其他任務 |
| 收到時間與時區 | 必要 | 建立當日時間窗與 Temporal QA 證據 |
| 匯入時間 | 必要 | 追蹤自動化延遲與重跑 |
| Gmail thread／message ID | 必要 | 去重與回溯原始郵件 |
| Drive 檔案位置 | 必要 | 原文保存與引用 |
| 原始連結 | 若有則必要 | 交叉核對一手來源 |
| 內容雜湊或等效版本識別 | 建議必要 | 辨識相同內容的重寄與修改版 |
| 處理狀態 | 必要 | `已匯入／重複略過／錯誤／待分級／已納入分析` |
| 資訊分級 | 分級後必要 | 框架級情報／背景事件／短線操作情報 |
| 審核狀態 | 分析前必要 | `未驗證／待 Manus 驗證／Manus 已完成核驗／CIO保留／CIO排除` |

**（草案條文 7｜去重、分級與證據拆分）**

今日工作區接收 Grok 輸入後，由 Manus 先執行去重、事件索引、時間標記、來源標記、數據與新聞來源核對及事實／推論／市場情緒區分，再依 SOP 現行資訊分級規則處理。單一 Grok 郵件若同時包含官方事實、第三方分析與 Grok 自身推論，必須按證據單位拆分，不得整封郵件套用單一證據等級或單一資訊分級。[1]

官方財報、法說、公告或可獨立取得的一手資料，應以其原始來源作為證據；Grok 的摘要可作為正式資訊來源中的索引、線索或第三方解讀，但不能取代一手來源。若一手來源未被取得或核對，相關項目應維持待驗證，不得因 Grok 使用肯定語氣而升級為已獲確認。

**（草案條文 8｜正式分析的進入條件）**

Grok 輸入只有在 Manus 完成數據與新聞來源核對、時間／期間核對、去重、證據拆分、資訊分級及必要的 Self-QA 後，才可被正式分析流程引用。若被分為框架級情報，應依現行九欄、Temporal QA、Evidence 三欄、五大框架與 Self-QA 規則處理；若被分為背景事件，依其證據性質決定是否套用九欄；若屬短線操作情報，僅可作節奏參考，不得自動觸發框架更新或正式治理結論。[1]

**（草案條文 9｜風控隔離）**

Grok→Drive 自動匯入不得觸發、計算、修改或取代正式風控官流程。任何涉及 MA21、MA81、正式收盤價、100／80／80／0 水位或極端波動附則的分析，仍須引用當日風控官正式輸出；若風控官結果未提供，必須標示「風控判定未提供，本次分析不含風控水位資訊」，不得以 Grok 郵件或前一日資料補足。[1] [2]

**（草案條文 10｜不得自動觸發的下游動作）**

Grok 郵件自動進入今日工作區，不得單獨觸發下列動作：正式九欄結論、Framework Update、持股加碼／減碼建議、風控水位變更、儀表板正式發布、正式治理文件修訂、深度研究啟動或結案摘要。這些動作仍須依現行 SOP 的正式流程與 CIO 裁定條件執行。

**（草案條文 11｜錯誤、缺漏與停用條件）**

若自動匯入出現來源不符、主旨格式改變、正文缺失、時間無法核對、附件無法讀取、重複率異常、Drive 寫入失敗或連續兩次未收到預期郵件，系統應將資料標記為錯誤或待確認並通知 CIO。系統不得以空白、前一日資料或模型記憶替代缺失內容。CIO 可要求暫停匯入、只保留原文、排除特定任務或恢復為純 CIO 直送模式。

**（草案條文 12｜保留與人工同步）**

若本介面條款經 CIO 核准並納入 SOP，完成版本更新後應建立獨立 Diff Summary，記錄受影響章節、資料流程、審核狀態、停止條件與測試結果；並依現行規則提醒 CIO 將需要同步的治理條款手動更新至其他獨立執行端。Grok 資料流本身不會使其他 AI 執行端自動取得新規則。

## 三、INDEX v1.4 條款草案

INDEX 的職責是導航與引用順序，不應在本次變更中新增分析規則。建議以「新增輸入介面導航」方式修訂，並明確宣告 Grok→Drive 不屬正式知識文件、不改變既有 Single Source of Truth。

### 建議新增至 Governance 或 Workflow 章節的條目

```text
`Grok→Drive 正式資訊來源與驗證介面`（正式登錄來源；內容須經 Manus 驗證）

用途：保存經 CIO 登錄條件篩選的 Grok 郵件原文、來源標記、收到時間、匯入時間、郵件識別碼、Drive 位置及可取得的原始連結，作為 Today's Workspace 的正式資訊來源輸入；內容先標示未驗證，經 Manus 核驗後才可作正式分析支持性輸入。

效力：本條目正式登錄 Grok 為資訊來源之一，但不建立新的治理層級，不改變 Constitution、Daily War Room SOP、AI 基本面追蹤框架、Risk Control 或 Portfolio 的優先順序；Grok 摘要必須經 Manus 完成數據、新聞、時間、證據與 Self-QA 驗證後，才可作正式分析支持性輸入，且不得直接視為 CIO 裁定。

處理：正式 Daily War Room 使用前，Manus 必須依 Daily War Room SOP 完成數據與新聞來源核對、時間／期間核對、去重、證據拆分、資訊分級及必要的九欄／Self-QA。Grok→Drive 不得自行觸發風控判定、Framework Update、Action Layer、儀表板正式發布或深度研究。

所有權威規則仍以 Constitution、Daily War Room SOP、AI基本面追蹤框架、MA21-81_100-80-80-0_正式規格書、風控官正式指令工作及 Portfolio 現行版本為準。
```

### 建議新增至 Analysis Execution Order 的說明

不建議把 Grok→Drive 插入正式文件讀取順序中，因為它不是治理規範或 Decision Layer 文件。可在正式讀取順序之前增加下列非規則性輸入說明：

```text
Today's Workspace 正式資訊來源輸入（須經 Manus 驗證）

在完成正式文件讀取後，Manus 可讀取當日由 CIO 提供或經核准介面匯入的 Grok 正式資訊來源內容。Grok 輸入必須標示未驗證／待 Manus 驗證狀態；讀取它不代表已採信其結論。Manus 必須先完成數據、新聞來源、時間／期間、證據核對與 Self-QA，任何正式分析仍須依 Daily War Room SOP 的資訊分級、證據拆分、九欄、風控引用與 Self-QA 規則執行。
```

### 建議新增至 Daily War Room 引用順序的說明

現行 Step 1–8 順序不應改動。可在 Step 8 之後、Official Daily War Room 之前補充一個輸入狀態說明，或在 Workflow 條目下加入下列文字：

```text
Today's Workspace 正式資訊來源規則：
CIO 直送內容與經核准的 Grok 正式資訊來源均可進入今日工作區；來源須分開標示。Grok→Drive 內容預設為未驗證／待 Manus 驗證，必須先完成數據、新聞來源、時間／期間、證據拆分、資訊分級與 Self-QA，才可成為正式分析的支持性輸入。它不得凌駕 Portfolio、Framework、Risk Control 或 Constitution，也不得改變既有引用順序。
```

### INDEX 版本紀錄草案

## 六、建議裁定文字

若 CIO 希望採取最低風險、最符合現行 CIO 直送模式的做法，可使用下列裁定文字：

> **核准 Grok→Drive 作為 AI Investment HQ 的正式資訊來源與驗證介面。核准範圍包括郵件保存、來源與時間標記、去重、未驗證／待分級狀態及提供今日工作區讀取；所有數據、新聞、來源連結與推論須先經 Manus 完成來源核對、數據驗證、時間／期間核對、證據拆分與 Self-QA，才可成為正式分析支持性輸入。不核准 Grok 直接產生風控判定、持股水位、Action Layer、儀表板結論或治理文件修訂。正式納入 SOP／INDEX 前，須完成資料契約、停止條件、Diff Summary、版本紀錄與受影響文件同步。**

此裁定文字只批准「輸入介面」而不批准「自動決策」，可以讓現有匯入流程具有正式定位，同時保留 CIO 對來源採信與下游分析的最終控制權。
