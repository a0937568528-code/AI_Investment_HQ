# Grok→Drive 資料流治理定位與每日自動化清單差距報告

**日期：** 2026-08-15  
**目的：** 將新啟用的 Grok→Gmail→Google Apps Script→Drive 資料流，放回 AI 投資總部目前的治理與每日工作清單中定位。  
**處理原則：** 本報告只做現況登錄與治理邊界說明；不修改憲章、SOP、知識索引、`AI協作治理架構.md` 或每日自動化工作清單原檔，也不把新資料流宣告為已核准的正式治理規則。

## 一、目前實際運作狀態

目前已啟用一條獨立的原始情報匯入管線：Grok 每日約 06:00 與 18:00 執行兩個搜尋任務並寄信至 Gmail；Google Apps Script 約於 07:00 與 20:00 搜尋 `noreply@x.ai`、排除 `New login` 主旨，將符合條件的郵件正文保存至 Drive `00_Grok` 的日期資料夾。首次正式匯入已成功處理 11 個 Grok threads，0 失敗、0 略過、0 附件；後續由每日早晚兩個時間觸發器執行。

這條管線只保存原始郵件，不會刪除 Gmail 郵件、不會標記已讀、不會封存、不會執行風控、不會產生投資結論，也不會直接建立 AI 投資總部的正式戰情室報告。Apps Script 觸發器是使用者 Google 帳戶內的外部設定，不是 Manus 內的每日戰情室排程。

## 二、依現行治理規範的正確定位

目前每日工作清單的正式方向仍是「CIO 提供原始情報、系統整理、風控官獨立判定、晚間完成正式統合」。因此，Grok 自動郵件不能直接被標示為 CIO 直送，也不能因已進入 Drive 就直接視為 Official Daily War Room 的正式輸入。[1] [2]

較合規的定位是：

> **Grok→Drive 是「外部原始情報收件匣／候選來源層」，不是正式分析層、風控層或決策層。**

其資料進入 AI 投資總部後，應保留寄件者、收到時間、原始主旨、Gmail message／thread ID、匯入時間及原文檔案位置；在沒有完成來源確認、資訊分級與今日工作區接收前，不得把內容直接當作已驗證事實或 CIO 正式指示。

## 三、與目前每日自動化清單的比對

| 每日清單節點 | 新 Grok→Drive 管線的關係 | 目前判定 |
|---|---|---|
| 01 每日基線載入 | 沒有直接關係；管線不載入治理文件 | 保持原規範 |
| 02 今日工作區接收 | 可作為候選原始資料入口，但尚未定義自動轉入今日工作區 | **部分對接** |
| 03 情報背景整理 | 目前只完成郵件保存，尚未執行去重、事件索引、事實／推論／情緒區分 | **尚未對接** |
| 04–07 收盤資料與風控 | 不應由 Grok 郵件管線觸發或取代 | **明確分離** |
| 08–14 晚間分析、九欄、框架、Action、Self-QA、Portfolio | 目前不自動啟動；需由正式工作流另行處理 | **尚未對接** |
| 15 儀表板封裝 | 不得由原始郵件直接產生 | **明確分離** |
| 16 正式資料歸檔 | `00_Grok` 目前是原始情報保存區，不等於正式資料夾 | **部分符合** |
| 17 規則異動同步提醒 | 新管線不是規則異動，暫不觸發治理升版 | **不觸發** |
| 18 結案摘要 | 不相關，不應自動產出 | **明確分離** |

## 四、目前新增的治理風險

第一個風險是**來源地位混淆**。Grok 的搜尋結果屬於第三方 AI 產出的研究／摘要，不是 CIO 的正式裁定，也不是風控官正式結果。若直接把 `00_Grok` 文件送入晚間正式分析，必須先標示其來源與證據等級，不能把 Grok 的敘述當成原始市場事實。

第二個風險是**CIO 直送規則的邊界被無意間改變**。目前 SOP 的核心模式是 CIO 把有價值資訊送入今日工作區；新增管線後，Grok 郵件會自動進入 Drive。這不必然違反規範，前提是它被當作候選來源層，而不是繞過 CIO 確認直接進入正式戰情室。若要把它定義為正式每日輸入來源，必須先由 CIO 明確裁定並更新 SOP／INDEX／版本紀錄。

第三個風險是**重複與時間窗問題**。目前 Apps Script 會保存最近三天符合條件的郵件，首次執行因此匯入了 2026-08-14 與 2026-08-15 共 11 封；之後靠 `AIHQ/Processed` 標籤與檔名避免重複。若 Grok 改變寄件者、主旨、時區或郵件格式，匯入可能漏資料或抓到非目標郵件，應將錯誤標籤與執行紀錄視為運維證據，而不是正式市場證據。

第四個風險是**外部自動化設定未進入 AIHQ 版本管理**。Apps Script 程式與觸發器存在於使用者 Google 帳戶中，未納入 GitHub 正式治理文件；因此若未記錄查詢條件、觸發時間、目標資料夾與最後測試結果，其他執行端無法重建此資料流。

## 五、目前不應做的事情

目前不應把 `00_Grok` 改名為正式研究或正式戰情室資料夾；不應把 Grok 郵件自動送進晚間九欄判定、風控判定或儀表板；不應因資料已經保存至 Drive 就勾選每日自動化清單第 1、2、3、6 或 7 項；也不應把這條管線寫成三層閘門已獲 CIO 核准的證據。

每日自動化工作清單原檔目前仍應維持「草案，尚未啟用為正式排程」。Grok→Drive 只能作為其外部輸入層的實際試運行紀錄，不能自動使整份清單升格為正式藍圖。

## 六、建議的下一個治理整理動作

目前最小且不越權的動作，是新增一份「Grok→Drive 資料流介面說明」至 `99_整理與封存`，記錄資料夾、觸發時間、Gmail 查詢條件、去重規則、資料欄位、錯誤處理與停止方式；本報告已先完成這個登錄。下一步若 CIO 要正式納入每日戰情室，應由 CIO 先裁定以下三件事：

| 待裁定事項 | 建議的治理問題 |
|---|---|
| 來源地位 | Grok 郵件是否只是候選來源，還是可直接作為每日今日工作區輸入？ |
| 審核閘門 | 是否要求 CIO／分析流程先完成來源確認與資訊分級，才能進入九欄與晚報？ |
| 文件同步 | 是否要在 SOP、INDEX 與每日清單中新增 Grok→Drive 介面條款，並建立 Diff Summary 與版本紀錄？ |

在 CIO 裁定前，建議維持現狀：Grok 自動匯入照常保存，AI 投資總部只把它視為未審核原始資料；正式分析、風控、儀表板與治理升版流程保持不變。
