# 團隊公告：Grok 郵件受限試運行合規操作須知

**公告日期：** 2026 年 8 月 15 日  
**公告對象：** AI Investment HQ 全體協作者、研究與資料處理人員  
**適用範圍：** Grok→Gmail→Google Apps Script→Google Drive `00_Grok`→今日工作區候選輸入流程  
**目前狀態：** 受限試運行；不等同正式治理規則，不等同 SOP v2.4／INDEX v1.4 生效。  
**依據：** CIO 核可書草案「採用 Grok 候選輸入介面」及相關核准前稽核程序；正式生效仍以 CIO 簽核與指定生效日為準。

## 一、公告重點

Grok 郵件目前可以作為 AI Investment HQ 的**外部候選原始情報來源**，用於保存、索引、來源核對與後續分級。它不是官方事實來源，不是風控官，不是 CIO 指示，也不是正式投資結論來源。

所有團隊成員必須記住以下區分：

> **自動匯入不等於已驗證；進入 `00_Grok` 不等於進入正式分析；進入待分級集合不等於取得採信或決策效力。**

## 二、目前允許的合規操作

### 1. 原始資料保存

符合既定 Gmail 條件的 Grok 郵件，由 Apps Script 自動保存至 Drive `00_Grok` 的日期資料夾。團隊成員可以查看原始郵件、主旨、寄件者、收到時間、匯入時間、thread／message ID、Drive 檔案位置與處理狀態。

目前介面基準為 `noreply@x.ai`、排除 `New login` 主旨、Apps Script 專案時區 `Asia/Taipei`，預期約 07:00 與 20:00 執行匯入。這些是本次試運行的設定，不得由個人自行修改；若來源、主旨、資料夾、時區、觸發時間或標籤需要變更，須先回報並取得授權。

### 2. 候選情報標記

若資料被放入今日工作區候選集合，必須維持以下狀態：

| 欄位 | 試運行要求 |
|---|---|
| 來源通道 | `source_channel=Grok` |
| 來源性質 | 第三方 AI 摘要／候選原始情報 |
| 審核狀態 | `未審核` 或 `待分級` |
| 一手來源 | 已取得並核對，或明確標示 `待驗證` |
| 處理狀態 | 已匯入／重複略過／錯誤／待分級 |
| 證據區分 | 事實、推論、市場情緒分開記錄 |

不得以「匯入成功」「Grok 說明」「標題看起來可信」等理由，把資料狀態改成「已確認」或「正式結論」。

### 3. 來源核對與資訊分級

團隊可以把 Grok 郵件當作研究線索，追查其引用的一手來源，例如公司公告、財報、法說資料或官方統計。Grok 自身的摘要與推論必須與一手來源分開保存；未能獨立核對的主張應維持「待驗證」。

正式分析前，必須依現行作業規範完成時間與期間核對、證據拆分、資訊分級及必要的 Self-QA。若資料屬短線操作資訊，只能作節奏參考，不得自動升級為框架級情報。

### 4. 原始資料的可追溯保存

任何引用 Grok 郵件的工作，必須能回溯到原始郵件與 Drive 檔案。不得只複製一段摘要而遺失寄件者、時間、主旨、原始連結或 thread／message ID。若發現同一內容重複匯入，應保留原始證據並標記重複，不得任意刪除或覆蓋。

## 三、明確禁止事項

試運行期間，任何團隊成員不得執行下列行為：

| 禁止事項 | 說明 |
|---|---|
| 把 Grok 摘要當成官方事實 | 除非已取得並核對一手來源，否則只能標示待驗證 |
| 把匯入成功當成 CIO 採信 | 技術成功只代表保存成功，不代表治理或內容核准 |
| 直接把 Grok 內容寫入正式九欄 | 必須先完成來源核對、證據拆分與資訊分級 |
| 以 Grok 郵件計算或改寫風控 | 不得計算 MA21／MA81、100／80／80／0、極端波動或持股水位 |
| 讓 Grok 觸發交易或持股行動 | 不得產生加碼、減碼、停損或交易執行指令 |
| 讓 Grok 自動觸發正式下游 | 不得直接觸發 Framework Update、Action Layer、儀表板正式發布、深度研究或結案摘要 |
| 修改正式治理文件 | 不得修改憲章、SOP、INDEX、風控規格、Portfolio 或家庭投資中心 |
| 修改 Apps Script 設定 | 不得自行改寄件者、查詢條件、觸發時間、資料夾、標籤或去重邏輯 |
| 刪除或覆蓋原始郵件 | 不得刪除 Gmail、清空 `00_Grok`、覆蓋既有原始檔或移除必要證據 |
| 默默放寬查詢條件 | 不得為了抓到更多郵件而移除 `New login` 排除條件或擴大來源範圍 |
| 把 GitHub 草案當成現行規則 | 整理分支的草案、FAQ、核可書與稽核程序都是審閱材料，未取代正式文件 |
| 自行宣稱已核可或已升版 | 介面門、流程門、版本門必須分開依 CIO 裁定，不能自行推定後一門已通過 |

## 四、標準處理流程

團隊成員若要使用 Grok 郵件，應按照以下順序處理：

1. **先確認來源。** 記錄寄件者、主旨、收到時間、原始連結、thread／message ID 與 Drive 位置。
2. **再確認狀態。** 將資料維持為「未審核／待分級」，不得直接標示已確認。
3. **再拆分內容。** 將原始事實、Grok 推論、第三方解讀與待驗證主張分開。
4. **再做來源核對。** 優先取得官方公告、財報、法說或其他一手資料；無法取得時保持待驗證。
5. **再做資訊分級。** 依現行 SOP 判斷框架級情報、背景事件或短線操作情報。
6. **最後才決定是否進入正式分析。** 任何九欄、風控、Action Layer 或儀表板輸入都必須走既有正式流程，不得由 Grok 匯入事件自動觸發。

## 五、異常回報與立即停止條件

發現以下任一情況，請立即停止使用該批資料進行正式分析，保留原始證據，並回報 CIO／指定維護者：

- 出現非 Grok 的 `noreply@x.ai` 郵件，或主旨格式與既定任務不符；
- 郵件正文、來源連結、收到時間或 thread／message ID 缺失；
- 同一郵件反覆建立新檔，或不同內容被錯誤判定為重複；
- 匯入日期與郵件收到日期不一致，且原因無法解釋；
- Apps Script 寫入失敗、錯誤沒有標記，或觸發器時間／時區異常；
- Grok 內容直接出現在正式九欄、風控輸出、持股水位、Action Layer 或正式儀表板；
- 任何人發現 Grok 內容與 CIO 指示、正式風控官結果、Portfolio 或一手來源衝突；
- 任何人要求刪除、覆蓋或隱藏原始郵件與匯入紀錄。

回報時至少提供：問題發生時間、郵件主旨、寄件者、thread／message ID、Drive 檔案位置、執行紀錄截圖，以及已採取的暫停或隔離動作。未完成調查前，不得以手動方式補寫正式結論。

## 六、責任分工

CIO 負責介面門、流程門與版本門的最終裁定；指定維護者負責 Apps Script、觸發器、Gmail 條件、Drive 資料夾與錯誤紀錄的技術維護；研究與分析人員負責來源核對、資訊分級、證據拆分與正式流程遵循；所有協作者都有義務回報異常，不得自行擴大 Grok 的治理效力。

在版本門仍暫緩期間，現行 SOP、INDEX、憲章、風控規格與每日自動化工作清單仍是正式依據。團隊不得以本公告自行宣告 SOP v2.4、INDEX v1.4 或任何新治理架構生效。

## 七、公告效力與覆核

本公告只適用於 Grok 郵件受限試運行，不構成正式治理文件升版，也不授予任何 AI 或團隊成員新的最終裁定權。若 CIO 撤回介面門或流程門核可，應立即停止候選輸入納入；若來源、資料流、下游用途或治理版本發生重大變更，必須重新稽核與呈核。

任何未列於本公告的使用情境，預設採較嚴格處理：只保存原始資料、標示待驗證、不得進入正式分析，直到取得明確裁定。
