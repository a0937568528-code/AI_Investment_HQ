# AI Investment HQ｜知識模型治理規範（Knowledge Model Governance Specification）

> **Status:** Official Governance Document（獨立治理文件，非任何研究文件之附屬）
> **Version:** v1.0
> **Effective date:** 2026-07-27
> **Owner:** AI Investment HQ
> **適用範圍：** 本規範為 `07_AI產業全景圖.md` 及未來所有知識地圖類文件（如未來新增之技術樹、生態系圖譜）之共同底層 Schema。`04`、`05`、`06` 等研究文件不受本規範直接拘束，但若涉及節點式知識結構，亦得引用本規範。

---

## 一、本規範存在的理由

07 類文件（知識地圖）若不預先定義節點顆粒度、連結類型與更新規則，極易發生兩種失敗模式：

1. **退化為公司研究文件**：節點內容逐漸加入財務數字、時效性新聞，與 `04_AI基礎建設投資分析.md` 職責重疊。
2. **架構無限重構**：每次新技術出現（如玻璃基板、Embodied AI）都引發節點分類方式的重新討論，導致文件維護成本失控。

本規範透過定義 Node、Connection、Projection、Atomic Unit 四項核心概念，以及一套明確的修訂流程（Version Governance），從根本上防止上述兩種失敗模式。

---

## 二、Node Naming Standard（節點命名規範）

**核心原則：Node 一律使用 Capability（功能性能力），不使用 Company（公司名稱）、Product（產品型號）、Technology Brand（技術品牌）。**

Node 分為兩層：

| 層級 | 定義 | 生命週期預期 | 範例 |
|---|---|---|---|
| **Capability Node（功能節點）** | 描述一種長期存在的功能性需求，不綁定特定技術實現方式 | 5 年以上，原則上不因技術演進而消失 | AI 運算能力、先進封裝能力、雲端基礎設施能力 |
| **Technical Instantiation（技術實現）** | 描述目前實現該功能的具體技術或公司代表 | 依技術週期變動，可能數季至數年更新一次 | GPU、ASIC（隸屬於「AI 運算能力」節點）；CoWoS、Glass Substrate（隸屬於「先進封裝能力」節點） |

**判斷測試：** 新出現的名詞，若是「解決既有功能性需求的新方法」，歸類為既有 Capability Node 下的 Technical Instantiation 更新（例如 Glass Core 歸入「先進封裝能力」）；只有當出現全新的、既有節點無法涵蓋的功能性需求時，才新增 Capability Node。

**禁止事項：** Node 名稱不得使用公司名稱（如「Hyperscaler」不得作為 Node，應為「雲端基礎設施能力」，Hyperscaler 公司群為其 Representative）；不得使用產品型號或技術品牌（如「Blackwell」「CUDA」不得作為 Node）。

---

## 三、Connection Standard（連結標準）

**核心原則：AI 生態系的節點關係不只有供應鏈（上下游），須明確標註連結類型，不得一律以單向箭頭表示。**

四種連結類型：

| 類型 | 代碼 | 定義 | 範例 |
|---|---|---|---|
| 技術依賴 | Tech | 節點 A 在技術上必須依賴節點 B 才能運作 | GPU 依賴 HBM、先進封裝依賴晶圓代工 |
| 商業依賴 | Biz | 節點 A 是節點 B 的主要客戶或採購方，非技術上的必要依賴 | Hyperscaler 是 GPU 之最大客戶 |
| 資本合作 | Cap | 節點 A 與節點 B 存在股權投資或資本合作關係 | Microsoft 投資 OpenAI、Amazon 投資 Anthropic |
| 價值流動 | Val | 節點 A 將能力輸出至節點 B，形成服務或產品交付 | 模型層透過 API 將智能能力交付應用層 |

同一對節點之間可以同時存在多種連結類型（例如 Microsoft 與 OpenAI 同時存在 Biz 與 Cap 關係），須並列標註，不得只擇一呈現。

---

## 四、Projection Standard（投影標準）

**核心原則：Knowledge（節點與連結的完整資料集）只有一份；View（呈現方式）可以有多種，View 不是 Knowledge 本身，不得將任一 View 誤植為唯一正確的知識結構。**

允許之 Projection 範例：
- Technology View（僅呈現 Tech 連結，用於理解技術供應鏈）
- Business View（僅呈現 Biz 連結，用於理解商業採購關係）
- Capital View（僅呈現 Cap 連結，用於理解資本合作網絡）
- Value Flow View（僅呈現 Val 連結，用於理解服務交付路徑）

07 文件之視覺化呈現，應標明其採用之 Projection 類型，不得將單一 Projection（如僅呈現供應鏈的 Technology View）當作 AI 生態系的完整表述。

## 五、Atomic Update Rule（最小維護單位）

**核心原則：知識庫的最小維護單位為 Technical Instantiation，不是 Capability Node。**

- 新增或調整 Technical Instantiation（如新增 Glass Core 至「先進封裝能力」節點下）：屬**日常維護**，可隨時更新，不須觸發架構討論。
- 新增或調整 Capability Node（如新增全新的功能性能力類別）：屬**架構變更**，須依本規範第六章 Version Governance 流程處理。
- 新增或調整 Connection 類型（如認為四種連結類型不足以表達某關係）：屬**架構變更**，須依 Version Governance 流程處理。

**自我檢驗機制（Knowledge Health Indicator）：** 若 Capability Node 或 Connection 類型的變更頻率接近甚至超過 Technical Instantiation 的變更頻率，即為 Schema 設計失敗之訊號，應立即停止填充內容，重新檢視本規範。

各文件預期更新頻率參考：

| 文件／層級 | 預期更新頻率 |
|---|---|
| Capability Node（本規範第二章） | 極低（設計目標：5 年以上不變） |
| Connection 類型（本規範第三章） | 極低 |
| Technical Instantiation（07 內容） | 半年至一年 |
| `04_AI基礎建設投資分析.md`（公司研究） | 每季 |
| `03_AI基本面追蹤框架.md`（判定規則） | 隨重大事件 |
| Daily War Room | 每日 |

## 六、Version Governance（版本治理）

**核心原則：本規範一旦凍結（Freeze）為 v1.0，任何後續修改須經下列流程，不得於個別分析或對話中逕自變更。**

修訂流程（RFC, Request for Change）：

1. **提案**：明確指出現行 Schema 無法涵蓋的具體案例，說明為何現有 Node／Connection／Projection 定義不足。
2. **實證要求**：至少提出兩個真實案例，證明現行 Schema 確實無法妥善分類，且新提案能解決該問題而不引發其他矛盾。
3. **Prototype**：以新提案重新套用於既有已收錄之全部案例，確認不產生回歸性錯誤（既有案例分類結果不因此改變或需要重新歸類的除外情況需明確列出並說明原因）。
4. **Review**：使用者確認提案與測試結果。
5. **版本更新**：正式更新本規範版本號，並登錄 `CHANGELOG.md`，說明變更內容與觸發原因。

**明確排除事項：** 本規範不因單一分析報告、單一對話討論或單次架構辯論而修改。架構層級之修改須完整走完上述五步流程。

## 附錄：Schema 壓力測試（原《知識模型治理規範_壓力測試.md》v1.0，2026-07-30 併入本文件）

> 依本規範第六章 Version Governance 要求，任何 Schema 於正式套用前須以真實案例驗證。本附錄為 07 正式撰寫前之強制驗證程序，測試對象為生態系中關係最複雜的五個節點代表。

### 測試案例一：NVIDIA

| 項目 | 分類結果 |
|---|---|
| 所屬 Capability Node | AI 運算能力 |
| Technical Instantiation | GPU（具體為 Blackwell 等架構世代，屬更下層之產品標籤，07 不收錄此層） |
| 連結類型 | Tech（依賴 TSMC 先進製程、依賴 SK hynix/Samsung/Micron 提供 HBM）／Biz（Hyperscaler 為其最大客戶）／Val（將運算能力交付予模型層與應用層） |
| 是否需要新增 Node？ | 否，「AI 運算能力」既有節點已涵蓋 |

**測試結果：通過。** NVIDIA 作為 Technical Instantiation 而非 Node 本身，符合 Node Naming Standard；其多重連結關係（Tech/Biz/Val 同時存在）驗證了 Connection Standard 必須支援多類型並存的設計是必要的。

### 測試案例二：Microsoft（作為 Hyperscaler 代表）

| 項目 | 分類結果 |
|---|---|
| 所屬 Capability Node | 雲端基礎設施能力 |
| Technical Instantiation | Hyperscaler（Microsoft Azure 為此節點下之 Representative） |
| 連結類型 | Biz（向 NVIDIA／AMD 大量採購 GPU）／Cap（投資 OpenAI）／Val（將雲端算力與 AI 服務交付予企業／應用層）／Tech（依賴晶圓代工、記憶體、封裝供應鏈之整體供給） |
| 是否需要新增 Node？ | 否 |

**測試結果：通過。** 此案例驗證了 Node Naming Standard 中「不得使用公司名稱作為 Node」的必要性——若當初以「Hyperscaler」為 Node，將無法容納 Microsoft 同時身兼採購方（Biz）、投資方（Cap）、服務供應方（Val）的三重角色；以「雲端基礎設施能力」為 Node、Microsoft 為 Instantiation，可完整表達此複雜度。

### 測試案例三：OpenAI

| 項目 | 分類結果 |
|---|---|
| 所屬 Capability Node | 基礎模型能力（Foundation Model Capability） |
| Technical Instantiation | OpenAI（GPT 系列模型，具體版本屬更下層產品標籤，07 不收錄） |
| 連結類型 | Cap（接受 Microsoft 投資）／Biz（向 Microsoft Azure 採購雲端算力，形成雙向 Biz 關係）／Val（將模型能力透過 API 交付應用層） |
| 是否需要新增 Node？ | 否 |

**測試結果：通過，且驗證了「供應鏈」改為「生態系」修正之必要性。** 若僅用單向供應鏈邏輯，OpenAI 與 Microsoft 的關係會被誤判為單純上下游；實際上兩者存在 Cap（投資）與雙向 Biz（OpenAI 向 Microsoft 採購算力，Microsoft 亦透過 OpenAI 技術強化自身產品）並存的複雜關係，證明 Connection Standard 四種類型缺一不可。

### 測試案例四：Broadcom

| 項目 | 分類結果 |
|---|---|
| 所屬 Capability Node | AI 運算能力（CSP 客製化路線） |
| Technical Instantiation | ASIC（協助 Google TPU、Meta MTIA 等客製化晶片設計） |
| 連結類型 | Biz（受 Hyperscaler 委託設計，屬服務提供關係而非自有品牌銷售）／Tech（依賴晶圓代工完成量產） |
| 是否需要新增 Node？ | 否，與 NVIDIA 同屬「AI 運算能力」節點，僅 Instantiation 不同（ASIC vs. GPU），代表同一 Capability 下可有多個平行 Instantiation，彼此構成替代或互補關係 |

**測試結果：通過。** 此案例驗證了同一 Capability Node 下可容納多個平行且互為競爭/互補關係之 Instantiation，Schema 不須為每一種技術路線各自開一個 Node。

### 測試案例五：台積電

| 項目 | 分類結果 |
|---|---|
| 所屬 Capability Node | 晶圓製造能力、先進封裝能力（同時隸屬兩個 Capability Node） |
| Technical Instantiation | 晶圓代工（3nm/2nm 製程）；CoWoS（先進封裝技術之一） |
| 連結類型 | Tech（NVIDIA、Broadcom、AMD 等技術上依賴其製造與封裝能力）／Biz（承接大量客戶委託代工訂單） |
| 是否需要新增 Node？ | 否 |

**測試結果：通過，且驗證了一個新規則需求。** 台積電同時是「晶圓製造能力」與「先進封裝能力」兩個 Capability Node 的 Instantiation，證明**單一公司可對應多個 Capability Node，並非一對一關係**。此為測試中發現、原規範未明文之細節，建議於下次 RFC 流程中列為候選修訂項目，但**本次不臨時修改規範**，先以此測試報告記錄該觀察，待實際撰寫 07 內容時如再次遇到類似情況，才正式提出 RFC。

### 壓力測試總結

| 案例 | 結果 | 關鍵驗證點 |
|---|---|---|
| NVIDIA | 通過 | 多重連結類型並存之必要性 |
| Microsoft | 通過 | Node 不得使用公司名稱之必要性 |
| OpenAI | 通過 | 供應鏈改生態系、雙向 Biz 關係之必要性 |
| Broadcom | 通過 | 同一 Capability 容納多個平行 Instantiation |
| 台積電 | 通過（附帶觀察） | 單一 Instantiation 可能對應多個 Capability Node，建議列入未來 RFC 觀察項目，本次不修改規範 |

**結論：** 五案例全數通過現行 Schema（v1.0），僅發現一項未來可能需要 RFC 討論的細節（單一公司對應多 Capability Node 之表達方式），依 Version Governance 原則，此非現行 Schema 之缺陷，不影響 Schema 凍結，僅記錄備查。Architecture Freeze v1.0 成立，可正式進入 07 內容撰寫階段（Knowledge Population Phase）。
